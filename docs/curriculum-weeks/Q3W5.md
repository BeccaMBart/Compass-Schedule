Q3W5 Weekly preparation

Build the published teacher timetable

Starting point: Publication snapshots exist; the teacher endpoint still needs its actual timetable output.

End-of-week check: Each teacher reads and prints only their own approved timetable.

Explain these ideas before the build

The API filters snapshot meetings by the authenticated Teacher mapping. Do not download all teachers' data and hide rows in the browser. Sort by numeric day and period order, not alphabetical labels. Show version/time, useful empty messages, and a print layout. Admin can inspect an approved timetable through authorized routes. Keep publication history immutable and never print a draft as though it were approved.

view: The information shown for a particular task.

order: The sequence in which records are displayed.

label: Text explaining a field or status.

Prepare this week in order

1. Confirm the previous checkpoint works. Prepare two teacher accounts with different published meetings, including Monday P1, Monday P2, and Tuesday P1.

2. Prepare the fictional records or paper examples named above. Prepare account/tool access only; do not implement this week’s app changes before the live lesson.

3. Practice this project-management action with students: Use a user journey: sign in, see own timetable, identify the version, print. Each step gets a check.

4. Improve the prompt by focusing on this skill: Specify the user, authorized data source, and visible result rather than asking for a generic dashboard.

5. Keep the three lessons below in order. If a check fails, use that lesson’s repair prompt and preserve the working data. Record failed or not-run checks honestly.

Student record for the week

Each student keeps one note with their name/pseudonym, role, prediction, small change or review, observed result, and one concept in their own words. Use docs/student-work/ for class evidence. The teacher remains responsible for the application and all account credentials.
